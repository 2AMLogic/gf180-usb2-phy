## Cause, per error-severity category

Three facts, measured directly off **the compare's own extracted layout
netlist** (`<block>_layout.spice`) and the reference netlist — not read out of
the tool's prose, and not inferred. `<block>-cause.json` holds them per block;
`scripts/analog_lvs.py` regenerates them on every run (`--no-analyze` skips
it).

### Cause A — PMOS bodies are on floating, unnamed wells (all five blocks)

The reference puts every PMOS body terminal on a named supply net. The layout
puts each PMOS body on its **own anonymous well net** (`\$9`, `\$10`, …), with
no tie to that supply:

| Block | PMOS devices | distinct layout PMOS body nets | reference PMOS body net |
|---|---|---|---|
| `differential_driver` | 17 | 17 (all anonymous) | `VDD` |
| `differential_receiver` | 4 | 4 (all anonymous) | `VDD` |
| `dplus_pullup` | 66 | 12 (all anonymous) | `VPU_REG` |
| `se_receiver_dm` | 4 | 4 (all anonymous) | `VDD` |
| `se_receiver_dp` | 4 | 4 (all anonymous) | `VDD` |

Evidence, `differential_receiver_layout.spice` vs
`differential_receiver_reference.spice`:

```
layout     M$8  \$7 AMPOUT VDD \$9  pfet L=0.28U W=32U      <- body \$9, an unnamed well
reference  XMP_B1 BUF1 AMPOUT VDD VDD pfet_03v3 L=0.28u W=32u  <- body VDD
```

Every PMOS therefore differs from its reference counterpart on one terminal,
and no PMOS can pair. The well geometry exists (KLayout synthesized a net for
it); what is absent is a **tap tying it to the supply**.

### Cause B — the p-substrate is not tied to a labelled ground (all five blocks)

Every NMOS body on the layout side lands on `vsubs`, the deck-synthesized
substrate net, on all five blocks. The reference puts them on `VSS`. And
**`VSS` does not exist as a named net in any of the five layouts** — it is
absent from every block's named-net list. Instead, `vsubs` is exported as a
top-level layout pin on all five.

```
layout     M$1 \$7 AMPOUT \$1 vsubs nfet   <- body vsubs (deck-synthesized); source \$1 unnamed
reference  XMN_B1 BUF1 AMPOUT VSS VSS nfet_03v3  <- body and source both VSS
```

This is why `body_verification.status` is `unverified` on every block: the
tool says as much in its own warning ("either no substrate-tap geometry is
drawn, or the drawn tap's net carries no name label").

### Cause C — the labelled port set is not the schematic's port set (all five blocks)

On **every** block, the set of named layout nets is exactly the set of layout
pins: names come only from text labels, and nothing else is named. The
labelled set is wrong in both directions — schematic ports are missing, and
internal nodes are exported as ports:

| Block | layout pins | reference ports | in common |
|---|---|---|---|
| `differential_driver` | `DM_GATEN DM_GATEP DM_PX DP_GATEN DP_GATEP DP_PX TXDM TXDP vsubs` | `VDD VSS TXDP TXDM TXOE DP DM` | `TXDM TXDP` |
| `differential_receiver` | `AMPOUT IBIASN VDD vsubs` | `VDD VSS DP DM RXD` | `VDD` |
| `dplus_pullup` | `DP NODE0..NODE5 PU_EN PU_ENB TRIM0..TRIM4 TRIM0B..TRIM4B vsubs` | `DP VPU_REG VSS PU_EN TRIM0..TRIM4` | `DP PU_EN TRIM0..TRIM4` |
| `se_receiver_dm` | `AMPOUT IBIASN VDD vsubs` | `VDD VSS DM RXDM` | `VDD` |
| `se_receiver_dp` | `AMPOUT IBIASN VDD vsubs` | `VDD VSS DP RXDP` | `VDD` |

`differential_driver` has **no `VDD` and no `VSS` pin at all**; `dplus_pullup`
has neither `VPU_REG` nor `VSS`. Internal nodes (`AMPOUT`, `IBIASN`,
`DP_GATEP`, `NODE0`, `TRIM0B`, …) are labelled as if they were ports.
Unnamed layout nets: 31 of 40 (`differential_driver`), 11 of 15 (each of
the three receivers), 14 of 34 (`dplus_pullup`).

### Why `net.unmatched` on three blocks and `net.split` on two

The two error categories track **how many net correspondences the comparer
could seed from**, read from each report's own `net_correspondence`:

| Block | seeded correspondences | net error category |
|---|---|---|
| `differential_driver` | 0 (`[]`) | `net.unmatched` 62 |
| `differential_receiver` | 0 (`[]`) | `net.unmatched` 25 |
| `dplus_pullup` | 2 (`DP`, `NODE1`, both pins) | `net.split` 13 |
| `se_receiver_dm` | 1 (`\$15` ↔ `DM`, not a pin) | `net.split` 5 |
| `se_receiver_dp` | 1 (`\$15` ↔ `DP`, not a pin) | `net.split` 5 |

The correlation is measured. The **mechanism** — that with zero seeds the
comparer can only report every net as having no counterpart, and that one or
two seeds let it propagate far enough to describe the remainder as a reference
net "divided across multiple layout nets" (the tool's own wording for
`net.split`) — is read from the tool's category descriptions and is
**inferred, not established here**. The 16 of 78 devices that pair on
`dplus_pullup` and the 4 of 13 on each single-ended receiver are the
downstream consequence of those seeds; which specific devices they are is in
each `-lvs-report.json`.

### What was NOT established

  labels repaired, so it is not shown that fixing them alone yields a match.
  Correcting them is the follow-up issue's work, and its result is the test.
- **The specific geometry responsible.** `layout/README.md` states the
  guard-ring / body-tie metal-1 pads each generator draws are in no plan net
  and so left unconnected. The measurements above are **consistent** with that
  and with the plan's pins being device terminals only — but the geometry was
  not stepped through, so the linkage from "pads in no plan net" to "these
  specific floating wells" remains an inference, not a finding.
- **Anything about device parameters.** With zero or near-zero device pairing,
  no W/L comparison took place. This record says nothing about whether the
  drawn sizes are right.

## Options used

**One, and it is output-side: `keep_extracted: true`.** It asks `klt lvs` to
write out the netlist it already built (below); it cannot change a verdict.

Nothing that relaxes the compare is set: no `parameter_tolerance`, no
`compare_parameters`, no `flatten_layout`/`flatten_reference`, no
`power_connectivity`, no `combine_devices`, no `netgen_setup`. The request is
layout `{file, deck: gf180mcu, top}` against reference `{netlist, top, form:
"subckt-call"}`, plus that one flag. `scripts/test_analog_lvs.py` pins that
the request carries no result-relaxing knob. The report's echoed `options`
block shows klt's defaults otherwise (`supply_nets: [GND, VCC, VDD, VGND,
VPWR, VSS]`, everything else false/null).

Confirmed by measurement, not assumption: the same five compares were first
run **without** `keep_extracted` and returned byte-identical verdicts — same
status, same device/net/pin counts, same error categories and counts on all
five blocks.

**Where the layout-side netlist comes from — and a correction.** Issue #345's
curator pass noted that `klt lvs --help` lists no option that writes the
extracted netlist, and inferred from that a tool gap to be filed upstream.
**That inference is wrong, and no friction issue was filed.** `keep_extracted`
is a *request* option, not a CLI flag; it exists and works on the pinned klt
0.9.0, writing the compare's own netlist to
`<request_dir>/.klt/lvs/<top>.spice` and naming it in
`environment.extracted_netlist`. The `null` the curator observed is simply
what a request that does not set it produces. (Pre-existing upstream context:
`2AMLogic/klayout-tools#1223`, which tunes `--check --rerun` around this very
field.)

So AC2's "extracted layout-side netlist" is taken from the compare itself, not
from a second extraction that might not be the netlist actually compared.

A standalone `klt extract` still runs, for the one thing `klt lvs` does not
emit: a structured per-device JSON report (device classes and counts,
per-device parameters and nets). **It is evidence only; the verdict is the
`klt lvs` run.** Both netlists are frozen and were diffed per block:

> They are identical on **every MOSFET**, and differ only in how resistors are
> carded — `klt lvs` writes `R$11 IBIASN VDD vsubs 200000 ppolyf_u_1k`, `klt
