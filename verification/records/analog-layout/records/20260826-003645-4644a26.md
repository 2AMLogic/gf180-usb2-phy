  **What genuinely changed upstream, verified against the new pin's own
  docs (`docs/cli/layout-plan.md`, `docs/cli/gen-compose.md` at
  `07b1f04`), not assumed:**

  1. **#1163 (device_map threading) landed, but doesn't reach this
     blocker.** `netlist.device_map` is now a real field on
     `klt.layout_plan.request/1` (`layout-plan.md:146`), "same shape and
     same ingestion path as `klt lvs`'s `reference.device_map`" — but the
     same doc line states its shipped limitation plainly: "every entry is
     resolved as a MOS-shaped (4-terminal) override, so mapping a non-MOS
     (e.g. 2-terminal resistor/capacitor) subcircuit raises a clear
     `device_map only supports MOS-shaped 4-terminal overrides today`
     error." `differential_driver`'s blocking device (`rm1`) is a
     2-terminal metal resistor, exactly the case the fix explicitly did not
     cover — so re-probing it (this run did, live, the same way the
     superseded record did) reproduces the identical error text.
  2. **#1166 (block orientation, mirror/rotate)** and the two-layer
     `routing.layer_role: "metal2"` via-drop routing role (closing the
     `#1168`/"issue #454" gap the superseded record's root-cause class 3
     named) are both real and documented (`gen-compose.md`'s "Block
     orientation" and "Via-drop routing" sections). **Neither is used by
     the committed plans under `layout/analog/plans/`**, because those
     plans predate both fields — every `device_groups[]` entry still has no
     `orientation` key, and no plan sets `routing.layer_role` to anything
     but the implicit single base layer. These are opt-in fields; landing
     upstream does not retroactively change what an unmodified plan asks
     for, which is exactly why the routed-net count is unchanged at 0/8,
     0/9, 0/9. Authoring plans that actually exercise them (per-group
     mirroring to fix the same-facing CMOS-inverter case; a `metal2`
     `VDD`/`VSS`/bias bus) is real per-block layout design work outside a
     mechanical re-run, and — per this issue's explicit "not in scope"
     section — this record does not attempt to grow that into a
     block-specific generator; it states plainly that the capability exists
     and is unused.
  3. **The router's diagnostic behaviour changed in a way that produces a
     new, independently-confirmed regression.** `gen-compose.md`
     (`nets[].legs[]`, "Since #1169, a net that could not be *fully*
     connected still draws every leg the spanning-tree search accepted")
     documents that a partially-routable net now keeps its successfully
     drawn legs. What this run's raw `nets[]` payloads
     (`differential_receiver-layout-plan.json` etc., in this record's
     `artifacts/`) show going further than that: legs whose own `reason`
     field reports a *rejected* candidate route (`routed: false`, e.g.
     `"backbone's 0.17um-wide drawn path crosses 1.29um through unrelated
     block 'mn_n_ina''s bbox"`) still leave measurable geometry in the
     output GDS. Every one of the 19/22/22 new `klt drc` violations (rule
     `metal1.width.1`, re-run separately from the script's own aggregate
     count so the full polygons are in this record's artifacts) is a
     4-vertex quadrilateral whose two long edges are exactly 0.17 µm apart
     — the backbone width the router itself quotes in its own rejection
     text — with the *opposite* short edge cut on a diagonal down to a
     single point, i.e. a mitered dead-end rather than a squared-off stub.
     A route that tapers to zero width at its unterminated end cannot
     satisfy any positive minimum-width rule by construction. This is
     new: the superseded record's three placeable blocks were DRC-clean
     specifically *because* an unrouted leg left no geometry at all before
     this change. Filed generically upstream — see "Friction filed" below.
  4. **`dplus_pullup`'s `nf=10` blocker is completely unmoved.** No
