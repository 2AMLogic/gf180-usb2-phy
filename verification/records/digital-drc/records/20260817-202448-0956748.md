# Record 20260817-202448-0956748

- **Record ID**: 20260817-202448-0956748

  This record states the **real** result, including the fact that it is
  not clean — per `CLAUDE.md` ("no claim without a testbench" / never

  clean results (or a documented, justified waiver)"). This is the
  documented, justified waiver.

- **Run configuration**: `PDK=gf180mcuD klt drc

- **Statistical convention**: N/A — single deterministic check against a

- **Result**:
  - `status: "violations"`, `violation_count: 153`.
  - `rule_counts`: `metal1.space.1`: 141, `metal1.width.1`: 12.
  - **Root cause, verified by direct comparison, not merely asserted**:
    1. The same standard-cell library GDS checked as an isolated single
       instance (`gf180mcu_fd_sc_mcu9t5v0__and2_1`, no placement context)
       is `status: "clean"`, `violation_count: 0` — the library's own
       geometry is DRC-legal in isolation.
    2. Every reported violation's `source_cell` names a standard-cell
       instance (`and2_1`, `aoi211_2`, `nand3_2`, `dffq_1`, ...), and every
       violation is on `Metal1` — the layer standard cells use for their
       own internal pin/power-rail geometry (`klt place-and-route`'s
       `io.layer_h`/`io.layer_v` route signals on `Metal2`+ per
       `docs/cli/place-and-route.md`'s documented gf180mcu routing range,
       `Metal2-Metal5` — `Metal1` is never a routed signal layer in this
       flow, only cell-internal geometry).
    3. `klt place-and-route`'s own documented v1 scope (`docs/cli/
       place-and-route.md`, "Out of scope") states plainly: "Tapcell
       insertion, power-grid generation (PDN), metal fill... none of
       these are part of the request/response contract this phase
       implements." At 40% target utilization, real (legally spaced, not
       overlapping) placement gaps exist between adjacent same-row
       standard-cell instances; each cell's own `Metal1` power/ground
       rail is drawn flush to its own cell boundary (so a *zero-gap*
       abutment forms one continuous rail — see finding 4), but a
       *nonzero* gap between cells with no filler cell bridging it leaves
       each cell's own rail edge exposed as a genuinely narrow / too-close
       `Metal1` shape relative to its neighbor.
    4. [klayout-tools#1028](https://github.com/2AMLogic/klayout-tools/issues/1028)
       (closed, `2AMLogic/klayout-tools`) already investigated exactly
       this mechanism for the zero-gap case and confirmed, directly
       against a real `gf180mcu_fd_sc_mcu9t5v0` corpus GDS: a true
       zero-gap row abutment is DRC-clean today (KLayout's own
       `merged_semantics` already tolerates it), but "a genuine sub-dbu
       residual gap ... between otherwise correctly-pitched instances
       does still report a real `metal1.space.1` violation on the shared
       power/ground rail. This is by-design, not loosened: the rail is
       drawn flush to the cell outline specifically so abutment forms one
       continuous rail, and a real place-and-route flow leaving such a
       gap has a genuine rail discontinuity." This record's 141
       `metal1.space.1` violations are the same mechanism at real
       (larger, 40%-utilization) inter-cell gaps, not a `klt drc` engine
       false positive — the question of "is this the check engine or the
       layout" is already closed by #1028 for this exact rule/mechanism.
  - **Overall: violations present, root-caused, not a fabricated pass.**
    This is a real gap in what `klt place-and-route` v1 produces on its
    own (no filler-cell/PDN stage), not a defect in `rtl/usb_utmi_phy.v`
    or a klt DRC-engine bug. Closing it requires either (a) a future `klt
    place-and-route` capability (filler-cell insertion / rail-stitching,
    already named in that command's own "Out of scope" section as a
    known-deferred v1 gap — no new friction issue needed, it is already
    tracked there) or (b) a follow-on issue in this repo running a
    filler-cell-insertion pass on `layout/digital/usb_utmi_phy.def`
    before final DRC/LVS signoff (T1 checklist items 3/4).
  - **LVS**: not attempted by this record — see the place-and-route
    record's "Coverage gaps" for why.
