# layout

GDS/OASIS and DRC/LVS evidence for this PHY. Two halves, tracked separately
because they landed at very different maturity (issue #25, T1 checklist item
2).

## Digital — `layout/digital/` (delivered, DRC-clean, LVS-matched)

`usb_utmi_phy.gds` / `usb_utmi_phy.def` / `usb_utmi_phy_routed.v` — the real
PHY digital logic (`rtl/usb_utmi_phy.v` and every submodule it instantiates:
the four vendored canonical protocol modules under `rtl/common/`
(`usb_nrzi_encoder`, `usb_nrzi_decoder`, `usb_bit_stuffer`,
`usb_bit_destuffer`, since #84) plus `usb_sync_detector`,
`usb_eop_detector`, `usb_line_state_decode`), synthesized (`klt synthesize`,
Yosys) and place-and-routed (`klt place-and-route`, OpenROAD) against the
gf180mcu `gf180mcu_fd_sc_mcu9t5v0` standard-cell library. Reproducible from
a committed, real request-file flow — see `flow/README.md`'s "Digital
synthesis + place-and-route" section for the exact commands, and
`verification/records/place-and-route/records/20261015-011501-32db02a.md`
for the measurement (regenerated by issue #131 from the post-#115/#112/#113/#130
source tree at `32db02a`, superseding the post-#84 run of issue #87): 330
mapped standard cells becoming 1155 placed instances (340 logic instances
including CTS buffers and dummy loads, plus 815 physical-only fill, endcap and
tap instances), die 34881.2 um2, 43.7 % utilization, 13140 um routed
wirelength, 0 setup/hold/antenna/router-DRC violations at the 12 MHz spec
clock rate, ~44.4 MHz `fmax` at the nominal liberty corner with estimated RC
(with the extracted parasitics actually attached: 42.6 MHz at `tt_025C_1v80`,
`verification/records/post-layout-pvt/records/20261015-011505-32db02a.md`), and
every one of the cell library's 15 liberty corners (1v8, 3v3 and 5v0
families) positive on both setup and hold (worst setup 27.4 ns at
`ss_125C_1v62`, worst hold 0.41 ns at `ff_n40C_5v50`). The routed
netlist, DEF and GDS are bit-for-bit reproducible: a second, newer klt
reproduced all three byte-identically.

**DRC-clean** — `verification/records/digital-drc/records/20261015-011502-32db02a.md`:
`klt drc --deck gf180mcu` reports `status: "clean"`, `violation_count: 0`
against this exact GDS.

**LVS-matched, power-verified** —
`verification/records/digital-lvs/records/20261015-011503-32db02a.md`:
gate-level LVS of this GDS against `usb_utmi_phy_routed.v` (the as-built,
post-CTS netlist) is a `status: "match"` **and**
`power_connectivity.status: "match"` — every power/ground pin of every
instantiated standard cell reaches its expected net — with the negative
control on a deliberately-broken reference correctly rejected. Driven by
`scripts/digital_lvs.py`, which asks `klt lvs` to compare the as-built
Verilog directly (`reference.form: "gate-level-verilog"`, the form
[klayout-tools#1336](https://github.com/2AMLogic/klayout-tools/issues/1336)
added to close
[klayout-tools#1419](https://github.com/2AMLogic/klayout-tools/issues/1419)
— the transcription half of this script this issue made deletable, exactly
as the old closing note predicted) and to prune the physical-only
filler/tap masters structurally instead of by name. The three flow-level
asymmetries the script's earlier hand-transcription handled
(physical-only fillers, unconnected CTS load pins, `assign`-aliased output
ports) are the tool's own disclosed warnings now
(`topology.power_only_pruned`, `topology.reference_port_alias_joined`).

**What that does and does not say.** The curated `gf180mcu` deck is klt's own
rule set, not the foundry sign-off deck; no metal/density fill is inserted, so
this is not a density-clean claim. LVS holds the standard cells as black boxes
— it verifies the *assembly*, not the foundry's library. There is no IO ring
or pad frame (core-only). Extracted-parasitic STA of this
layout is recorded separately under
`verification/records/post-layout-pvt/` — three liberty corners with extracted
wire and vertical-coupling capacitance attached (current record
`20261015-011505-32db02a`), not a SPICE re-simulation of this netlist and not
RC signoff. A net being *name-matched* in the SPEF is not evidence its
parasitics were attached: the earlier records (`20260922-042422-9ec2304`,
`20261008-200000-8139bb6`; the latter's fix is `20261008-195826-74ccfac`) reported full name annotation while OpenSTA applied
no wire capacitance (`delay_changed: false`). The current record discloses 7
unannotated drivers (floating CTS dummy-load outputs) and 3 partially
unannotated drivers (`RxActive`, `LineState[1:0]`), no wire RC delay (lumped
capacitance), an ideal clock, and no lateral coupling (none declared); see
`manifests/README.md` item 5.digital. The older name-annotation counts in
`20260905-182000-80d4593.md` were not re-checked for attachment.

**History.** Until 2026-08-25 this layout was **not** DRC-clean: 153 `Metal1`
space/width violations at standard-cell row gaps, root-caused to
`klt place-and-route`'s v1 scope having no filler-cell / power-rail-stitching
stage, and cross-checked against
[klayout-tools#1028](https://github.com/2AMLogic/klayout-tools/issues/1028).
That record
(`verification/records/digital-drc/records/20260817-202448-0956748.md`) is
superseded, not deleted — it remains the correct account of what a PDN-less
place-and-route produces. The fix was upstream: `klt` 0.3.0 added the optional
`request.power` block (tapcell + `pdngen` + `filler_placement`), which
`flow/request-usb-utmi-phy-par.json` now uses.

A net counts as routed only when a flat conductivity
extraction over metal1/via1/metal2/via2/metal3 puts all of its pins in one
component that no other net's pin shares, and as a cross-check KLayout's own
`LayoutToNetlist` finds exactly one wired net per plan net (20/8/9/9/21). Negative controls
(one track's vias deleted; an extra metal-2 bridge) were seen to be reported as an open and a
short respectively.

**klt limit hit, with the run.** With the klt of the first delivery (`7ee09483`,
0.7.1.dev1743 — the pin these counts were measured under, 2026-10-27)
the plan path routes `dplus_pullup` 6/21 and the three receivers 1/8, 1/9, 1/9 —
the same counts as the 2026-09-21 run — and rejects every other leg with
"backbone ... crosses N um of block 'X''s interior on the side *away* from its own
pin" (issue #1895 protection), even with `routing.cross_block_layer_role`
set to `metal2` (tried on `differential_receiver`: IBIASN and LOADDIODE then route, the
other five still do not). This is the multi-net layer/track-assignment gap
recorded as `2AMLogic/klayout-tools#1962` (open). The pin has moved twice since
that run: to klt 0.8.0 on 2026-10-27 (`f10baec`), under which all four GDS were
recorded as reproducing (`fdff78c`), and to klt 0.9.0 on 2026-11-06 (issue #263,
`102faa6`), which regenerated all four streams under new hashes — so the streams
committed today are the 0.9.0 ones, and `layout/analog/provenance.json` records
the klt each was written by. The remaining nets are
completed by scripted routes in `scripts/gen_analog_layout.py`:

- every plan places one row of tall vertical devices, so gate pins (a metal-1 pad
  on top) escape **up** and everything else (full-height source/drain strips,
  resistor heads) escapes **down**; each pin gets a via1 on its own metal-1 and a
  0.28 um metal-2 stub, and each net a metal-3 track (0.70 um pitch, never shared)
  above or below the row;
- a net with both kinds is joined by one metal-2 corridor in a gap between two
  devices (gate and source/drain stubs of one device are 0.43 um apart, closer
  than metal-2 spacing, so they never share a side);
- no device is moved or re-sized. The one geometry-adjacent change is that
  top-level instance origins are snapped to the 0.005 um manufacturing grid
  (only `dplus_pullup` is affected: 7 instances).

**How `dplus_pullup` became DRC-clean (DR-0010).** At klt `7ee09483`
(0.7.1.dev1743), the pin at the 2026-10-27 run, a bare `dplus_pullup` plan run

device placed to the right of the first fractional-width resistor. The origin snap

`r_seg0`–`r_seg4`, whose netlist lengths (0.343, 0.686, 1.371, 2.743, 5.486 um)
are not on the grid. Both gaps are filed as `2AMLogic/klayout-tools#4202` (group
origins not snapped) and `#4203` (`res_array` sub-grid lengths). The operator
ruled on 2026-10-30 (issue #251) to set the no-re-sizing rule aside for these five
resistors only: `spec/decisions/0010-dplus-pullup-trim-resistor-grid-snap.md`
gives each an on-grid drawn length (0.420, 0.685, 1.370, 2.745, 5.485 um; XR0 is
lengthened because 0.345 um fails `pplus.width.1`/`sab.width.1`), set as

#263 (2026-11-06):** klt 0.9.0 ships klayout-tools#4666, so the plan no longer

## Regenerating

Both halves need `scripts/setup-env.sh`'s environment (venv + pinned `klt` +
gf180mcu PDK) — see `docs/environment-setup.md`.

```bash
./scripts/setup-env.sh
source .venv/bin/activate

# --- digital: synthesis -> place-and-route -> routed GDS (layout/digital/)
ln -sf "$(pwd)/scripts/openroad-docker.sh" .venv/bin/openroad   # if no native openroad
PDK=gf180mcuD klt synthesize flow/request-usb-utmi-phy-synth.json --format json
cp flow/.klt/synthesize/run-*/usb_utmi_phy_synth.v flow/.klt/synthesize/usb_utmi_phy_synth.v   # the P&R request names this path
PDK=gf180mcuD klt place-and-route flow/request-usb-utmi-phy-par.json --format json
cp flow/.klt/place-and-route/usb_utmi_phy.gds layout/digital/usb_utmi_phy.gds
cp flow/.klt/place-and-route/usb_utmi_phy.def layout/digital/usb_utmi_phy.def
cp flow/.klt/place-and-route/usb_utmi_phy.v   layout/digital/usb_utmi_phy_routed.v

# --- digital signoff: DRC, then gate-level LVS (+ its negative control)
PDK=gf180mcuD klt drc layout/digital/usb_utmi_phy.gds \
    --deck gf180mcu --top usb_utmi_phy --format json
PDK=gf180mcuD python3 scripts/digital_lvs.py
PDK=gf180mcuD python3 scripts/digital_lvs.py --negative-control
klt erc layout/digital/usb_utmi_phy.gds layout/digital/erc-supply-spec.json \
    --top usb_utmi_phy --format json   # T1 item 11; exit 4 = antenna half not_checked, expected

# --- analog: execute the committed layout plans, complete the routing, DRC each result
PDK_ROOT=$HOME/.volare .venv/bin/python scripts/gen_analog_layout.py            # text report
PDK_ROOT=$HOME/.volare .venv/bin/python scripts/gen_analog_layout.py --format json
PDK_ROOT=$HOME/.volare .venv/bin/python scripts/gen_analog_layout.py --deliver   # rewrite layout/analog/*.gds + provenance.json
PDK_ROOT=$HOME/.volare .venv/bin/python scripts/gen_analog_layout.py --check     # reproduce every gds_sha256 in a scratch dir
```

`scripts/gen_analog_layout.py` writes each block's klt result
(`<block>.klt.gds`), the routed GDS, its raw Phase C response JSON, and a
combined `analog-layout-report.json` under `layout/analog/out/` (gitignored
scratch), and prints one verdict line per block; `--deliver` copies the routed
GDS of every block in `DELIVERABLE_BLOCKS` (now all five) to `layout/analog/`
and merges their entries into `provenance.json`; `--blocks <name>` narrows a
run, and the merge leaves the other blocks' entries untouched. Its exit code is about *the run*, never about the quality of the
layout: `0` means every plan executed (with `--check`: and every hash
reproduced), `1` means the run itself failed (no klt, no PDK, unexpected
exception), `3` means `--check` found a mismatch. Read the report for the
verdict — a full run now ends `analog layout DELIVERED`, every plan having
executed, routed fully and come back DRC-clean.

As of issue #72 every one of the five analog blocks executes from a
committed plan (`differential_driver.json` was the last to be authored, once
klayout-tools#1731 gave `res_array` drawn-geometry support for gf180mcu
metal resistors), so the driver no longer carries a plan-less-block path
(removed in issue #177; it is in git history if a future block needs one).

`scripts/digital_lvs.py` writes its extracted/reference netlists and reports
to `layout/digital/lvs/` (gitignored scratch — the frozen copies live under
`verification/records/digital-lvs/`). It exits 0 only on a full pass —
`status: "match"` **and** `power_connectivity.status: "match"` with every
declared expected net exercised; with `--negative-control` it exits 0 only
when the compare correctly *fails* on a deliberately broken reference.

See `flow/README.md` for the digital flow's full detail and
`verification/README.md` for the evidence-record convention that
`verification/records/place-and-route/`, `verification/records/digital-drc/`,
`verification/records/digital-lvs/`, and
`verification/records/analog-layout/` all follow.
